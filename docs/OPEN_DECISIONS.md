## 1. 지도 SDK 확정 — ✅ **결정됨: Kakao Maps**

`kakao_map_sdk` (네이티브, `com.kakao.vectormap`).

**결정 사유**: 성능이나 지도 품질이 아니라 **API 키 발급 가능성**.
NCP(네이버) 가입이 실제로 막혔다 — 휴대폰 인증번호 미수신, ID 찾기도 실패.
카카오 개발자 사이트는 카카오 계정으로 네이티브 앱 키가 즉시 나온다.
쓸 수 없는 키를 기다리는 것보다 오늘 움직이는 스택이 낫다.
([비교표와 감수 사항](ARCHITECTURE.md#naver-vs-kakao))

초기 분석에서 "카카오는 WebView 플러그인뿐"이라고 판단했는데 틀렸다.
`kakao_map_plugin`(WebView)만 보고 `kakao_map_sdk`(네이티브, 5일 전 릴리스)를 놓쳤다.

**대가로 감수하는 것**: 클러스터링 직접 구현(약 60줄), 에뮬레이터 사용 불가(x86 미지원),
젊은 패키지(likes 10).

**되돌릴 조건**: NCP 가입이 풀리고 + 직접 만든 클러스터링이 실기기 기준에 미달이면 Naver가 우위.
Naver 빌드 검증은 이미 끝나 있어(`spike/map_spike`) 되돌리는 비용은 작다.

**Google Maps**는 한국 지도 데이터 제약으로 계속 배제.

## 2. 앱 프레임워크 확정 — ✅ **결정됨: Flutter**

Phase 1 스파이크를 Flutter로 완주했고 실기기 측정이 통과했다
(p95 6.9ms / janky 0.3%, 마커 1000개). 되돌릴 이유가 없다.

`kakao_map_sdk`는 Flutter 전용 네이티브 래퍼다. RN으로 가면 카카오 네이티브 지도를
쓸 수 있는 유지되는 라이브러리가 사실상 없고, Expo 관리형에서는 더더욱 어렵다
([근거](ARCHITECTURE.md#2-앱-프레임워크-비교)).

> 원래 "React에 능숙하고 Dart 경험이 없다면 뒤집힐 수 있다"고 남겨뒀던 항목이다.
> 답을 받지 못한 채로 Flutter 스파이크가 통과했으므로 Flutter로 확정한다.
> **Dart가 부담이라면 지금 말해야 한다** — Phase 3부터는 되돌리는 비용이 급격히 커진다.

## 3. 신규 스팟 즉시 노출 vs 사전 검수

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 즉시 노출 + "미검증" 배지** (추천) | 등록자가 즉시 결과를 본다 → 기여 동기 유지. 콜드스타트 시기에 중요 | 허위 스팟이 잠깐 노출됨 |
| B. 운영자 승인 후 노출 (최대 24h) | 품질 보장 | 등록했는데 안 보이면 이탈. 운영자가 병목 |
| C. 하이브리드 — 신규 계정만 사전 검수 | 균형 | 구현·운영 복잡도 증가 |

**추천: A.** 사진 필수 + 로그인 필수 + rate limit이 이미 있고
([신뢰도 장치](TRUST_AND_MODERATION.md#3-신뢰도--평판-점수는-만들지-않는다)),
초기 물량이 적어 운영자가 하루 안에 전부 본다. 노출 리스크 창이 짧다.

**물어야 할 것**: 허위 스팟이 하루 노출되는 것과, 등록자가 "내 스팟이 안 보인다"고
느끼는 것 중 어느 쪽이 더 나쁜가?

## 4. 즐겨찾기를 MVP에 포함할 것인가

현재 [Should](MVP_SCOPE.md#should--mvp에-있으면-좋지만-없어도-출시된다)로 분류.

**포함 시 따라오는 것**: `favorites` 테이블, 저장 목록 화면, 상세의 저장 버튼,
저장 시 로그인 요구 흐름. 대략 화면 1개 + 테이블 1개.

**추천: 포함.** "다음에 가볼 곳을 모아두는" 행위는 발견의 자연스러운 다음 단계이고,
로그인할 이유를 하나 더 만든다. 구현 비용도 작다.

**빼야 할 경우**: Phase 7 시점에 일정이 밀려 있다면 가장 먼저 잘라낼 항목이다.

## 5. 로그인 수단 범위

| 안 | 비고 |
|---|---|
| 카카오만 | 한국 사용자 커버율은 높다. **iOS 심사에서 Apple 로그인 요구 가능** |
| **카카오 + Apple** (추천) | iOS 심사 요건 충족. 구현 부담 작음 |
| + 익명 로그인 | 등록 마찰을 줄이지만 **책임 없는 쓰기가 되어 오염 방어가 무너진다** |
| + 이메일 | 쓸 사람이 거의 없다 |

**추천: 카카오 + Apple (iOS).** 익명 로그인은 넣지 않는다 —
로그인을 요구하는 이유가 편의가 아니라 **책임**이기 때문이다.

**확인 필요**: 소셜 로그인 제공 시 Apple 로그인이 필수인지 현재 App Store 심사 정책 확인
([검증 항목](ARCHITECTURE.md#6-착수-전-검증이-필요한-항목)).

## 6. 위치정보사업 신고 필요 여부 — 법률 확인

현재 설계는 **개인위치정보를 수집·저장·제3자 제공하지 않는다.**
사용자 위치는 단말에서만 쓰이고 서버에는 지도 bbox만 간다
([상세](ARCHITECTURE.md#개인정보)).

그래도 위치정보법상 **위치기반서비스사업 신고 대상인지 확인이 필요하다.**
설계로 판단할 문제가 아니다.

**해야 할 일**
- 방송통신위원회 위치정보 관련 안내 확인
- 애매하면 법률 자문 (스타트업 대상 무료 상담 창구 활용 가능)
- 결과에 따라 **위치기반서비스 이용약관**을 별도로 준비

**시점**: Phase 8(베타) 이전. 출시 직전에 발견하면 일정이 밀린다.

## 7. 사진 저작권 정책 범위

| 안 | 장단 |
|---|---|
| **본인 촬영만 허용** (추천) | 분쟁 소지 최소. 등록 마찰은 늘어남 |
| 제3자 사진 허용 + 출처 기재 | 시드 확보가 쉬움. **저작권 분쟁 리스크** |

**추천: 본인 촬영만.** 약관에 명시하고, 등록 폼에 한 줄 안내를 넣는다.
신고 접수 시 즉시 `is_hidden` 처리.

**함께 정해야 할 것**
- 업로드 사진의 이용 범위 (서비스 내 표시 / 홍보물 사용 / 제3자 제공)
- 탈퇴 시 사진 처리 — 스팟 정보로서 유지할 것인가, 삭제할 것인가
  (추천: 유지. 삭제하면 스팟 정보가 무너진다. 단 약관에 명시해야 한다)
- 인물이 찍힌 사진 처리 (초상권)

## 8. 스팟 노출 통제 — "알려지면 막힌다" 문제

[P4 페르소나](PRODUCT_REQUIREMENTS.md#p4-로컬-스케이터--시딩-파트너--태준)의 실제 걱정이다.
좋은 스트리트 스팟이 널리 알려지면 사람이 몰리고, 민원이 들어오고, 결국 막힌다.
**이 앱이 스팟을 죽이는 도구가 될 수 있다.**

| 안 | 비고 |
|---|---|
| A. 아무 통제 없음 | 단순. 로컬 스케이터의 등록 기피 가능 |
| B. "민감 스팟" 플래그 — 상세 정보를 로그인 유저에게만 | 최소 장치. 구현 작음 |
| C. 등록자가 공개 범위 선택 (전체 / 로그인 유저) | 통제감을 주지만 UX·데이터 복잡도 증가 |
| D. 랭킹·추천 기능을 아예 안 만듦 | **이미 채택함** ([Won't](MVP_SCOPE.md#wont--mvp에서-만들지-않는다)) |

**추천: MVP는 D만. B는 시딩 파트너 인터뷰 결과를 보고 결정.**
실제 스케이터들이 이 문제를 얼마나 크게 느끼는지 먼저 들어야 한다. 추측으로 만들 기능이 아니다.

**확인 방법**: Phase 5 무렵 시딩 파트너 모집 시 직접 물어본다.

## 9. 하드 삭제 예외 정책

원칙은 [삭제하지 않는다](TRUST_AND_MODERATION.md#0-세-가지-원칙)이다. 상태만 바꾼다.
하지만 예외가 필요한 경우가 있다.

- 토지 소유자·관리자의 삭제 요청
- 초상권·저작권 침해 신고
- 개인정보가 포함된 사진·설명
- 수사기관 요청

**정해야 할 것**: 어떤 경우에 `hidden`으로 충분하고, 어떤 경우 물리 삭제하는가.
누가 승인하는가. 기록은 어떻게 남기는가.

**추천**: 기본은 `hidden`. 물리 삭제는 **법적 요구가 있을 때만**, 운영자 2인 확인 후.
삭제 이력은 별도 로그로 남긴다.

## 11. iOS 검증·빌드 환경

현재 개발 환경은 **Windows**다. iOS 빌드·실행·스토어 제출에는 **macOS + Xcode가 반드시 필요**하다.
에뮬레이터나 우회 수단으로 대체되지 않는다.

이건 선택이 아니라 제약이고, 두 가지를 결정해야 한다.

**(1) 스택은 Android 결과만으로 확정했다 — iOS는 언제 확인할 것인가?**

Phase 1은 Android 실기기 측정(PASS)만으로 종결했다. `kakao_map_sdk`는 iOS 13+를 지원하고
Swift 네이티브 래퍼가 있지만 **이 프로젝트에서 검증된 적이 없다.**
Android가 되면 iOS도 대체로 되지만 보장은 아니다.

**추천: macOS 확보 시점을 Phase 3 이전으로 잡는다.**
Android만으로 Phase 2~3을 전부 진행할 수 있고, 그 사이에 환경을 마련하면 일정 손실이 없다.
Phase 4(인증) 이후에 iOS가 막히면 되돌리는 비용이 급격히 커진다.

**(2) macOS를 어떻게 확보할 것인가?**

| 안 | 비고 |
|---|---|
| Mac 구입/보유 | 가장 확실. 초기 비용 |
| 맥 클라우드 대여 (시간당) | 검증·빌드만 필요하면 충분히 싸다 |
| CI의 macOS 러너 | 빌드 자동화까지 겸함. 대화형 디버깅은 어려움 |
| **iOS를 1차 출시에서 제외** | Android 먼저 출시. 한국 스케이터 중 iOS 비중을 감안하면 손실이 클 수 있다 |

**물어야 할 것**: 타깃 사용자의 iOS 비중을 감당할 수 있는가? 감당 못 하면 macOS 확보는
선택이 아니라 필수 비용이고, 지금 계획에 넣어야 한다.

## 결정이 개발을 막는 순서

구현에 착수하려면 아래 순서로 필요하다.

```
지금 필요       →  없어도 되는 것
─────────────────────────────────────────
#2 (프레임워크)  ✅ Flutter 확정
#1 (지도 SDK)    ✅ Kakao 확정
#5 (로그인)      ← Phase 4
#3 (검수 여부)   ← Phase 5
#7 (사진 정책)   ← Phase 5
#8 (노출 통제)   ← Phase 7 (인터뷰 후)
#4 (즐겨찾기)    ← Phase 7
#9 (삭제 정책)   ← Phase 6
#6 (법률)        ← Phase 8
#10 (이름)       ← Phase 8
```

**#1·#2는 Phase 1에서 종결됐다.** 다음으로 답이 필요한 건 **#5(로그인 수단, Phase 4)**이고,
**#6(위치정보법)** 과 **#11(macOS)** 은 리드타임이 길어 지금부터 알아봐야 한다.
