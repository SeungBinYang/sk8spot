# MVP 범위

> 판단 기준은 하나다: **"이 기능이 없으면 초기 유저가 스팟을 발견하거나 공유할 수 없는가?"**
> 아니라면 Must가 아니다.

MoSCoW 사용. **Won't = "안 만든다"가 아니라 "MVP에서 안 만든다"**.

## Must — 이게 없으면 앱이 아니다

| 기능 | 왜 필요한가 | 비고 |
|---|---|---|
| **지도 홈 (비회원)** | "내 주변 탈 곳" 질문의 유일한 답 경로. 앱의 정체성 | 지도 이동 시 해당 영역 스팟 조회 |
| **마커 + 클러스터링** | 서울 도심은 스팟이 겹친다. 클러스터 없으면 마커 더미가 된다 | 카카오 SDK에 없어 **직접 구현** (지리 격자 버킷팅, 약 60줄) |
| **내 위치 버튼** | 현우(P3) 시나리오의 시작점 | 버튼 누를 때 권한 요청 (실행 시 X) |
| **스팟 상세** | 갈지 말지 판단하는 화면. 앱의 가치가 실제로 전달되는 곳 | 사진, 타입, 장애물, 바닥, 난이도, 킥아웃 위험, 실내외, 조명/야간, 상태 배지, 마지막 확인일 |
| **길찾기 연동** | 상세를 봤으면 가야 한다. 직접 만들면 미친 짓 | 네이버/카카오맵 앱 열기 |
| **스팟 등록** | 공급이 없으면 서비스가 없다 | **사진 1장 필수**, 나머지 필드 최소화 |
| **사진 업로드** | 텍스트만으로는 스팟을 판단할 수 없다. 허위 등록 억제 장치 1순위 | |
| **중복 감지 UX** | 같은 계단이 5개로 등록되면 지도가 쓰레기가 된다 | 상세: [TRUST_AND_MODERATION](TRUST_AND_MODERATION.md#중복-스팟-방지) |
| **상태 제보** | 스팟 정보가 썩는 문제의 유일한 해법. 이 앱과 일반 장소 앱의 차이 | 아직 있어요 / 없어졌어요 / 못 타요 / 정보 틀려요 |
| **로그인 (등록·제보 시점)** | 책임 없는 쓰기는 즉시 오염된다 | 카카오 + Apple. 열람은 비회원 |
| **스팟 공유** | 핵심 컨셉 3번. 카톡으로 "여기 가자"가 실제 사용 방식 | OS 공유시트 + 딥링크 |
| **신고 (부적절/허위)** | 스토어 심사 요구사항이기도 하다 (UGC 앱) | 상태 제보와 별개 경로 |
| **운영자 도구** | 자동 규칙만으로는 악성 등록을 못 막는다 | **별도 앱 안 만듦** — Supabase 대시보드 + SQL 뷰 |

### Must에서 일부러 뺀 것

- **회원가입 화면** — 소셜 로그인만 쓰므로 별도 가입 폼이 없다
- **온보딩 튜토리얼** — 지도 앱은 열면 이해된다. 튜토리얼이 필요하면 UX가 틀린 것
- **어드민 웹앱** — 초기 물량(일 10건 미만)에 어드민 UI를 만드는 건 순수 낭비

## Should — MVP에 있으면 좋지만, 없어도 출시된다

| 기능 | 판단 |
|---|---|
| **즐겨찾기(저장)** | 발견에 직접 붙는 기능이라 Must에 가깝다. 다만 저장 목록 화면이 따라오므로 범위가 커진다 → [결정 필요](OPEN_DECISIONS.md) |
| **필터 (스팟 타입)** | 스케이트파크 ↔ 스트리트 구분만 있어도 체감이 크다. **초기엔 이 하나만** |
| **지명 검색** | "홍대", "여의도"로 지도 이동. 없으면 손으로 지도를 끌어야 한다 |
| **기존 스팟에 사진 추가** | 중복 감지 UX가 이 기능으로 흘려보내므로 사실상 세트다. 없으면 중복 전환이 막다른 길이 된다 |
| **마지막 지도 위치 기억** | 재실행 체감 속도를 크게 올린다. 구현 5줄 |

> 중복 감지 → "사진 추가"로 전환하는 흐름을 Must로 잡았다면, 사진 추가도 Must여야 한다.
> 이 짝을 깨지 말 것.

## Could — 출시 이후 이른 시점

| 기능 | 판단 |
|---|---|
| 한 줄 후기 | 별점 리뷰보다 가볍고 스팟 맥락에 맞다. 다만 모더레이션 비용 발생 |
| 추천 수 (좋아요) | 정렬 신호로 유용. 초기엔 표본이 없어 무의미 |
| 최근 본 스팟 | 로컬 저장으로 충분. 서버 불필요 |
| 필터 확장 (난이도, 야간, 실내외) | 스팟 수가 수백 개를 넘어야 필터가 의미를 가진다 |
| 목록 뷰 (거리순) | 지도를 못 읽는 사용자를 위한 대안 경로 |
| 스팟 수정 제안 | MVP는 "정보 틀려요" 제보로 대체. 필드 단위 수정 제안은 나중 |

## Won't — MVP에서 만들지 않는다

각각 **왜 안 하는지**가 중요하다. 그냥 미루는 게 아니다.

| 기능 | 제외 이유 |
|---|---|
| **댓글** | 스팟당 댓글 3개 달리는 게 최선의 시나리오. 모더레이션 비용만 생긴다 |
| **별점 리뷰** | 스팟은 식당이 아니다. "이 계단 4.2점"은 정보가 아니다. 난이도·킥아웃 위험이 진짜 축이다 |
| **스케이터 프로필 / 팔로우** | SNS가 된다. 이 앱은 장소 DB지 인맥 서비스가 아니다 |
| **같이 탈 사람 모집 / 세션 모집** | 실시간 매칭은 임계 유저 수가 필요하다. 초기엔 빈 게시판만 남는다 |
| **영상 업로드** | 스토리지·트랜스코딩 비용이 즉시 발생. 판단에는 사진이면 충분 |
| **트릭 기록** | 개인 기록 앱은 다른 제품이다 |
| **스팟 랭킹** | 랭킹은 곧 트래픽 집중 → 인기 스팟 킥아웃 유발. **서비스에 해롭다** |
| **사용자 레벨 / 뱃지 / 업적** | 게이미피케이션은 기여량이 0일 때 아무것도 못 한다. 유저가 생긴 뒤 검토 |
| **지역별 커뮤니티** | 게시판을 만드는 순간 이 앱은 카페가 된다 |
| **방문 인증 (GPS 체크인)** | 흥미롭지만(신뢰도 활용 가능) 위치 스푸핑 대응 비용이 크다. Phase 2 이후 |
| **다국어 / 해외 지역** | 초기 범위는 서울/수도권. 밀도 없는 확장은 가치가 없다 |
| **PC 웹** | 스팟은 밖에서 찾는다 |
| **푸시 알림** | 보낼 내용이 없다. "내 스팟에 제보 달림" 정도는 나중에 |

## 범위 방어선

기능 추가 요청이 오면 이 순서로 묻는다.

1. 스팟을 **발견**하거나 **등록**하거나 **공유**하는 데 필요한가? → 아니면 Won't
2. 필요하다면, 그게 **없을 때 사용자가 무엇을 못 하는가?** 대답이 모호하면 Could
3. 스팟 수가 100개일 때도 의미가 있는가? (랭킹·필터·추천은 전부 여기서 걸린다)
4. 이 기능이 **스팟을 망가뜨릴 위험**은 없는가? (랭킹·노출 확대 계열)

## Must 기능 ↔ 사용자 흐름 대조

모든 Must가 실제 흐름으로 커버되는지 확인용. 흐름 상세는 [USER_FLOWS](USER_FLOWS.md).

| Must | 커버하는 흐름 |
|---|---|
| 지도 홈, 마커/클러스터, 내 위치 | F1, F2 |
| 스팟 상세, 길찾기, 공유 | F3 |
| 등록, 사진, 중복 감지, 로그인 | F4 |
| 상태 제보, 신고 | F5 |
| 운영자 도구 | 흐름 밖 (운영 프로세스 → [TRUST_AND_MODERATION](TRUST_AND_MODERATION.md)) |
