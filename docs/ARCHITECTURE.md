## 0. 이 프로젝트의 기술적 성격

일반적인 CRUD 앱이 아니다. 두 가지가 전부를 지배한다.

1. **한국 지도 SDK를 크로스플랫폼 프레임워크에서 쓸 수 있는가** ← 최대 리스크
2. **지리 공간 쿼리(bbox / 반경)를 얼마나 쉽게 하는가**

나머지(인증, 폼, 이미지 업로드)는 어떤 스택으로도 비슷하다.
**그래서 스택 선택은 지도와 지오 쿼리를 기준으로 결정한다.**

### Google Maps를 배제하는 이유

Google Maps는 플러그인 지원이 가장 좋지만, **한국에서는 지도 데이터 반출 규제로
건물·보행로·소규모 지형 정보가 국내 서비스보다 눈에 띄게 부족하다.**

이 앱은 "**저 건물 앞 계단 5단**"을 찾는 앱이다. 사용자는 마커 주변의 건물 모양과
보행로를 보고 위치를 맞춘다. 기반 지도가 부실하면 **앱의 기능 자체가 망가진다.**
플러그인 편의성으로 상쇄할 수 있는 종류의 문제가 아니다.

### Naver vs Kakao

지도 품질은 둘 다 충분하다. **둘 다 네이티브 래퍼가 존재한다** — 카카오는 WebView뿐이라는
초기 판단이 틀렸다 (`kakao_map_plugin`만 보고 `kakao_map_sdk`를 놓쳤다).

| | Naver `flutter_naver_map` | Kakao `kakao_map_sdk` |
|---|---|---|
| 네이티브 | ✅ (APK에 `libnavermap.so` 확인) | ✅ (`com.kakao.vectormap`) |
| 유지보수 | 271일째 릴리스 없음 | **5일 전 릴리스, 활발** |
| **API 키 발급 난이도** | **NCP — 휴대폰 본인확인 + 결제수단 등록** | **카카오 계정만 있으면 즉시** |
| 클러스터링 | **SDK 내장** (`NClusterableMarker`) | **없음 — 직접 구현** |
| 지원 ABI | armeabi-v7a, arm64-v8a, **x86_64** | armeabi-v7a, arm64-v8a (**x86 미지원**) |
| 에뮬레이터 | 가능 | **불가 — 실기기 필수** |
| 성숙도 | likes 116 | likes 10 (젊다) |

**결정적 요인은 성능이 아니라 API 키 발급 가능성이었다.**
NCP는 휴대폰 본인확인과 결제수단 등록을 요구하고, 실제로 이 프로젝트에서 **가입이 막혔다**
(인증번호 미수신, ID 찾기도 실패). 반면 카카오 개발자 사이트는 카카오 계정으로 앱을 등록하면
네이티브 앱 키가 바로 나온다.

쓸 수 없는 키를 기다리는 것보다, **오늘 움직이는 스택**이 낫다.

**→ 확정: Kakao Maps (`kakao_map_sdk`).**

#### 감수하는 것

1. **클러스터링을 직접 만든다.** 줌 레벨에 맞춘 지리 격자 버킷팅 + 개수 버블. 약 60줄이고
   MVP 스팟 수(150~300개)에서는 충분하다. 구현은 `spike/kakao_spike/lib/main.dart`의
   `clusterize()`에 있고, 검증되면 실제 앱으로 옮긴다
2. **에뮬레이터를 못 쓴다.** x86/x86_64 미지원. 개발 중 항상 실기기가 필요하다
3. **패키지가 젊다** (likes 10). 활발하지만 트랙 레코드가 짧다.
   지도 SDK를 [얇은 추상화로 감싸는 이유](#대비책)가 여기서 더 커진다
4. **Android 추가 설정이 필요하다** — 위치·인터넷 권한, 키 해시 등록,
   release 빌드용 proguard keep 규칙(`-keep class com.kakao.vectormap.**`).
   R8이 SDK를 지우면 release에서만 죽는다

#### 운영상 주의 — 카카오맵 무료 쿼터는 앱 하나에 묶인다

카카오맵 일간 무료 쿼터는 **계정에서 가장 먼저 활성화한 앱 하나에만 영구 귀속**된다.
이후 만든 앱은 받지 못하고, 기존 앱을 비활성화해도 옮길 수 없다.

이 프로젝트는 **카카오 앱 `sk8spot` (ID 1581809)** 에 쿼터가 귀속된 상태다.
실서비스 앱도 **반드시 이 앱을 재사용**하고, 패키지명만 네이티브 앱 키에 추가/수정한다.
"프로덕션용 앱을 새로 만들자"는 판단이 곧 무료 쿼터 포기가 된다.

#### Naver로 되돌릴 조건

NCP 가입이 풀리고, 직접 만든 클러스터링이 실기기에서 기준 미달이면 Naver가 다시 우위다.
빌드 검증은 이미 끝나 있으므로(`spike/map_spike`) 되돌리는 비용은 작다.

> **스파이크에서 남은 확인 항목** (기기·앱키 필요)
> - 마커 1000개 + 자체 클러스터링 실기기 스크롤 성능 (p95 ≤ 16.7ms)
> - 클러스터 버블 탭 → 확대 → 마커 분리가 자연스러운지
> - 지도 위 커스텀 마커 이미지 (스팟 타입 4종 아이콘)
> - 중앙 고정 핀 좌표 + `getBounds()` bbox
> - iOS는 macOS 확보 후 별도 확인 → [결정 필요](OPEN_DECISIONS.md) 11
>
> 판정 기준과 실행 방법: `spike/README.md`

### 대비책

지도 SDK는 **얇은 추상화 레이어 하나를 두고 감싼다.** 앱 전역에서 SDK 타입을 직접 쓰지 않는다.

```
MapView(
  markers: List<SpotMarker>,      // 앱 자체 타입
  onCameraIdle: (Bounds) -> void,
  onMarkerTap: (spotId) -> void,
)
```

인터페이스 하나짜리 추상화는 보통 과잉설계지만, **여기서는 교체 가능성이 실재하는 리스크**다.
단, 추상화는 위 4개 정도로 끝낸다. SDK 기능을 전부 감싸지 않는다.

| 스토리지 | Storage + 이미지 변환 | Cloud Storage |

| 비용 | 무료 티어 → 정액 + 사용량 | 무료 티어 → 종량 |

### Supabase를 택하는 이유

이 앱은 본질적으로 **지오 쿼리 앱**이다.

- Firestore에서 bbox 조회를 하려면 geohash 문자열 범위 쿼리를 쓰고, 오버페치한 뒤 클라이언트에서
  거르고, 여기에 "타입 = street" 필터를 더하려는 순간 막힌다
- PostGIS는 `geom && st_makeenvelope(...)` 한 줄이고 GiST 인덱스가 붙는다

두 번째 이유는 **모더레이션 데이터가 관계형**이라는 점이다.
"서로 다른 유저 3명이 30일 내 같은 유형 제보" ([상태 전이 규칙](TRUST_AND_MODERATION.md#스팟-상태-전이-규칙))는
SQL에서는 자연스럽지만 Firestore에서는 집계 문서를 손으로 유지해야 한다.

세 번째는 **운영**이다. SQL 콘솔이 있으면 [어드민 앱을 안 만들어도 된다](TRUST_AND_MODERATION.md#5-운영-프로세스--어드민-앱을-만들지-않는다).

### ⚠️ Supabase 내장 Kakao 프로바이더의 함정 — account_email 강제

Phase 4에서 실제로 겪은 문제라 기록해둔다. Supabase의 `signInWithOAuth(kakao)`는
**항상 `account_email` + `profile_image` 스코프를 강제로 요청한다**
(요청 시 넘기는 `scopes` 파라미터는 대체가 아니라 **추가**로 붙는다).

카카오의 이메일 동의항목(`account_email`)은 **비즈 앱 전환(본인인증) 없이는
동의항목 자체를 켤 수 없다.** 미인증 개인 개발자 앱에서 이 스코프를 요청하면
`KOE205 / invalid_scope: account_email`로 **로그인이 시작도 못 하고 막힌다.**

**해결책 두 갈래**:

| | 본인인증 후 비즈 앱 전환 | OIDC 직접 구현 (**채택**) |
|---|---|---|
| 필요한 것 | 카카오 본인인증(휴대폰 등) — **사업자등록증 불필요** | 없음(신원 확인 불필요) |
| 구현 변경 | 거의 없음 | 로그인 흐름 전체를 직접 구현 |
| 이 프로젝트가 고른 이유 | — | 사용자가 본인인증을 원치 않음 |

**채택한 구조**: Kakao 콘솔에서 **OpenID Connect를 ON**으로 켜고,
`scope=openid profile_nickname`(이메일 없음)으로 **앱이 직접** 카카오
`/oauth/authorize`를 호출한다. 돌아온 인가 코드는 `kakao-oidc`
Supabase Edge Function이 `/oauth/token`으로 교환해 `id_token`만 클라이언트에
돌려주고, **`client_secret`은 그 함수 밖으로 나가지 않는다.** 클라이언트는
`signInWithIdToken(provider: kakao, idToken: ...)`으로 세션을 만든다.

이때 authorize 요청의 `client_id`는 **REST API 키**를 써야 한다.
카카오 네이티브 SDK(네이티브 앱 키 기준 id_token)로 이 흐름을 타면 Supabase
쪽에서 `Unacceptable audience in id_token` 오류가 나는 게 알려진 문제라
([supabase/auth#1715](https://github.com/supabase/auth/issues/1715)),
반드시 REST API 키 기반 OIDC 코드 흐름으로 가야 한다.

구현: `app/lib/auth.dart`, `supabase/functions/kakao-oidc/`.
웹에서 로그인 왕복 검증 완료 (2026-09-23) — 프로필 자동 생성까지 확인.
모바일은 코드는 있으나 실기기 미검증 (`app_links`로 딥링크 처리).

## 4. 추천 조합

```
Flutter  +  Kakao Maps  +  Supabase (Postgres + PostGIS + Auth + Storage)
```

| 레이어 | 선택 | 근거 요약 |
|---|---|---|
| 앱 | Flutter | 한국 지도 플러그인 상황 + 마커 렌더링 |
| 지도 | **Kakao Maps** (`kakao_map_sdk`) | 한국 지도 품질 + 네이티브 + **키 발급이 실제로 가능** |
| DB | Supabase Postgres + PostGIS | 지오 쿼리가 SQL 한 줄, 관계형 모더레이션 |
| 인증 | Supabase Auth + **카카오 OIDC 직접 구현** (Edge Function), Apple 예정 | 내장 프로바이더는 account_email 강제로 막혀 우회 필요 (위 참조) |
| 이미지 | Supabase Storage | 같은 스택 안에서 RLS로 권한 일관 |
| 서버 로직 | DB 함수 + 트리거 | 상태 전이는 트리거가 가장 단순하다 |
| 운영 | Supabase 대시보드 + SQL 뷰 | 어드민 앱 안 만듦 |
| 상태관리 | Flutter 기본 + 가벼운 것 하나 | **지금 정하지 않는다.** Phase 3에서 필요한 만큼만 |
| 푸시 | **없음** | MVP에 보낼 알림이 없다 |
| 분석 | **없음 또는 최소** | 위치 앱에 서드파티 SDK를 넣기 전에 개인정보 영향 검토 |

### 일부러 넣지 않은 것

| 흔히 넣는 것 | 안 넣는 이유 |
|---|---|
| 별도 API 서버 (Node/Nest) | Supabase가 REST/RPC를 제공한다. 서버를 하나 더 운영할 이유가 없다 |
| GraphQL | 쿼리가 5개다 |
| Redis 캐시 | 트래픽이 없다. PostGIS 인덱스로 충분 |
| CI/CD 풀세팅 | Phase 8 전까지 로컬 빌드로 충분 |
| 상태관리 라이브러리 사전 선택 | 화면 3개짜리 앱에 아키텍처를 먼저 깔지 않는다 |
| 에러 트래킹 (Sentry 등) | Phase 8(베타)부터. 그전엔 볼 사용자가 없다 |

## 5. 위치 기반 서비스 처리

### 위치 권한

| 항목 | 결정 |
|---|---|
| 요청 시점 | **앱 실행 시 요청하지 않는다.** "내 위치" 버튼 탭 시 |
| 권한 종류 | `whileInUse` 만. **백그라운드 위치 요청 안 함** |
| 거부 시 | 정상 경로로 취급. 지도 이동으로 모든 기능 사용 가능 |
| 정확도 | 지도 이동용은 `balanced`면 충분. 스팟 등록 시에만 `high` |

권한을 나중에 요청하는 것이 UX 요구사항([F1](USER_FLOWS.md#f1-처음-앱을-설치한-사람))이자
권한 허용률을 높이는 방법이다. 맥락 없이 뜨는 권한 팝업은 거부당한다.

### 개인정보

- **사용자의 현재 위치를 서버로 보내지 않는다.** 서버에 가는 것은 지도 bbox 좌표뿐이다
- 위치 이력·경로를 저장하지 않는다
- 사진 EXIF의 GPS는 **업로드 전에 클라이언트에서 제거**한다
- 앱 내 저장(로컬)은 마지막 지도 중심 좌표 하나뿐이다

> **위치정보법상 위치기반서비스사업 신고 필요 여부는 법률 확인이 필요하다.**
> 개인위치정보를 수집·저장·제3자 제공하지 않고 단말 내에서만 쓰는 구조라도
> 사업 형태에 따라 판단이 달라질 수 있다 → [결정 필요](OPEN_DECISIONS.md) 6

### 지도 데이터 조회

```
지도 카메라 idle
  ↓ 400ms debounce
  ↓ 직전 조회 bbox 대비 이동량 < 화면 30%  AND  줌 변화 없음  →  skip
  ↓
spots_in_bbox(min_lng, min_lat, max_lng, max_lat, limit 200)
  ↓
마커 diff 적용 (전체 재생성 X — 새로 생긴 것만 add, 벗어난 것만 remove)
```

- **bbox 방식을 쓴다.** 반경 검색은 원형이라 화면(사각형)과 어긋나 모서리 스팟이 누락된다
- 반경 검색은 **중복 탐지에만** 쓴다 (`spots_near`)
- `limit 200`은 클러스터링과 조합하면 충분하다. 화면에 200개 이상 마커가 필요한 상황은 없다
- bbox를 화면보다 20% 넓게 요청하면 소폭 이동 시 재요청이 줄어든다

### 마커 성능

| 스팟 수 | 대응 |
|---|---|
| ~수천 개 (MVP) | 자체 클러스터링(지리 격자 버킷팅) + bbox limit 200 |
| 수만 개 | 줌 레벨이 낮을 때 서버에서 격자 집계 반환 (개수만) |
| 그 이상 | 벡터 타일 검토 |

**MVP에서는 첫 번째 줄만 한다.** 서울/수도권 스팟 수백 개 규모에서
서버 클러스터링을 미리 만드는 것은 순수 낭비다.

### 오프라인

MVP에서 오프라인 지원을 하지 않는다. 다만 다음 두 가지만 챙긴다.

- 마지막 지도 중심 좌표 로컬 저장 (재실행 체감 속도)
- 네트워크 실패 시 기존 마커를 지우지 않고 유지 + 재시도 배너
