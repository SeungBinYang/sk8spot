# 신뢰도 · 상태 관리 · 운영 정책

> 필드와 테이블 정의는 [DATA_MODEL](DATA_MODEL.md). 이 문서는 **그 값을 어떤 규칙으로 바꾸는가**를 다룬다.

사용자 생성 콘텐츠 서비스의 진짜 난이도는 기능이 아니라 여기에 있다.
동시에 **초기에 과하게 만들면 아무도 없는 데 감시탑만 짓는 꼴**이 된다. 균형점을 이렇게 잡았다.

## 0. 세 가지 원칙

1. **한 명의 말로는 아무것도 바뀌지 않는다.** 제보 1건은 배지만 띄운다
2. **되돌리기 어려운 변화에는 사람이 개입한다.** 철거·금지 판정은 운영자 승인
3. **삭제하지 않는다.** 상태만 바꾼다. 철거된 스팟도 기록으로 남는다

## 1. 스팟 상태 전이 규칙

### 전이 다이어그램

```
                     ┌──────────────────────────────┐
                     │           active             │ ← 기본값
                     └───┬──────────────────────┬───┘
       cant_skate ×3     │                      │     gone ×3
      (30일, 서로 다른    │                      │   (30일, 서로 다른
        유저, 자동)       ▼                      ▼      유저)
              ┌──────────────────┐     ┌──────────────────┐
              │     caution      │     │ [운영자 검토 큐]  │
              │ temporarily_closed│    └────────┬─────────┘
              └────────┬─────────┘              │ 승인
      still_there ×2   │                        ▼
      또는 운영자 확인   │              ┌──────────────────┐
                       └──── active ◀──│     removed      │ (복구 가능)
                                       │    no_skating    │
                                       └──────────────────┘

    운영자 단독:  any ──▶ hidden  (허위 / 권리침해 / 스팸)
```

### 규칙 표

| 제보 유형 | 1건 | 누적 조건 | 결과 |
|---|---|---|---|
| `still_there` (아직 있어요) | **즉시 반영** | — | `last_verified_at = now()`, `verify_count++`, 열린 제보 카운트 감쇠 |
| `cant_skate` (지금은 못 타요) | 배지만 | 서로 다른 유저 3명 / 30일 | 자동 → `caution` 또는 `temporarily_closed` (사유에 따라) |
| `gone` (없어졌어요) | 배지만 | 서로 다른 유저 3명 / 30일 | **운영자 검토 큐로.** 자동 전환 안 함 |
| `wrong_info` (정보 틀림) | 배지만 | 2건 이상 | 운영자 검토 큐 |
| `wrong_location` (위치 틀림) | 배지만 | 2건 이상 | 운영자 검토 큐 |
| `duplicate` (중복) | — | 1건부터 | 운영자 검토 큐 |
| `inappropriate` (신고) | — | 1건부터 | 운영자 검토 큐. 심각 사유는 즉시 `hidden` 가능 |

### 왜 `gone`은 자동 전환하지 않나

`removed`는 사실상 스팟을 지도에서 지우는 것이다.
악의적 유저 3명(또는 계정 3개)이 담합하면 멀쩡한 스팟이 사라진다.
**되돌리기 비용이 가장 큰 변화이므로 사람이 본다.** 운영자는 사진 증빙과 로드뷰로 대부분 1분 안에 판정할 수 있다.

반면 `caution`은 "조심하세요" 수준이라 오탐의 피해가 작고, 잘못되면 `still_there` 제보로 자연 복구된다.

### 자동 감쇠

- `still_there` 제보 1건 → 같은 스팟의 열린 `cant_skate` 제보 1건을 `resolution = 'rejected'`로 닫는다
- 상태가 `caution`인 스팟에 `still_there`가 2건 쌓이면 → `active`로 자동 복귀
- 열린 제보가 90일간 추가 제보 없이 방치되면 자동으로 닫는다 (일시적 상황이었을 가능성)

### 시간 기반 배지 (상태 변경 아님)

| 조건 | 상세 화면 표시 |
|---|---|
| `last_verified_at` 180일 초과 | 회색 "정보 확인 필요 · 마지막 확인 N개월 전" |
| 열린 제보 1건 이상 | 노란 "최근 제보가 있어요 (N건)" |
| 등록 후 운영자 미검토 | "미검증" (→ [결정 필요](OPEN_DECISIONS.md) 항목 3에 따라 달라짐) |

배지는 **파생값**이다. 컬럼으로 저장하지 않고 조회 시 계산한다. 배치 잡을 만들 필요가 없다.

### 구현 위치

상태 전이는 **`spot_reports` insert 트리거**에서 처리한다.
클라이언트가 `spots.status`를 직접 update할 수 없게 RLS로 막는다.

```
사용자 제보 → spot_reports insert
              → trigger: 같은 spot_id + kind의 열린 제보를
                         서로 다른 reporter_id 기준으로 카운트
                         (report_weight = 0인 유저는 제외)
              → 임계값 도달 시 spots.status 갱신 또는 운영 큐 플래그
```

## 2. 중복 스팟 방지

**중복을 막는 것보다, 중복 시도를 기여로 바꾸는 게 낫다.** 이게 설계의 중심이다.

### 1차: 등록 흐름 안에서 (가장 효과적)

[F4 흐름](USER_FLOWS.md#f4-새로운-스팟을-등록하는-사람)대로, 위치를 지정하는 **순간에** 감지한다.
정보를 다 입력한 뒤 "중복입니다"라고 하면 사용자는 앱을 지운다.

```
핀 이동 중 → spots_near(lng, lat, radius) 호출 (throttle)
          → 후보 있으면 주변에 회색 마커로 표시
          → "여기로 지정" 탭 시 [중복 확인 시트]
               "혹시 이 스팟인가요?"
               ┌────────────────────────────┐
               │ [사진] 홍대 앞 3단  · 12m   │
               │ [사진] 홍대 렛지    · 38m   │
               └────────────────────────────┘
               [ 네, 이 스팟이에요 ]  → 스팟 상세 + 사진 추가 모드
               [ 아니요, 다른 곳이에요 ] → 등록 계속
```

"네"를 누르면 **등록이 아니라 기여**가 된다. 사진 1장이 늘고, `last_verified_at`이 갱신된다.
중복 방지가 데이터 품질 향상으로 바뀌는 지점이다.

### 2차: 서버 측 플래그

"아니요"를 눌러도 실제로 중복일 수 있다. 차단하지 않고 플래그만 단다.

| 조건 | 처리 |
|---|---|
| 반경 30m 이내 + 같은 `spot_type` | `moderation_flag = 'pending_duplicate'` → 운영 큐 |
| 반경 10m 이내 (타입 무관) | 동일 |

**등록을 막지 않는다.** 실제로 계단과 렛지가 5m 거리에 따로 있을 수 있다.
사람이 보고 판단한다.

### 반경을 타입별로 나눈 이유

스케이트파크나 광장은 부지가 넓다. 같은 파크의 반대편 끝은 100m 이상 떨어진다.
50m 고정이면 대형 스팟의 중복을 놓친다.

| 타입 | 반경 |
|---|---|
| `street`, `diy` | 50m |
| `skatepark`, `plaza_park` | 150m |

### 하지 않는 것

- **이름 유사도 매칭.** 한국 스팟 이름은 제각각이다 ("홍대 3단" / "상수동 계단" / "그 계단").
  신호 대비 오탐이 너무 많다
- **자동 병합.** 두 스팟을 합치면 어느 사진·제보가 누구 것인지 엉킨다. 운영자가 한쪽을 `hidden` 처리한다

## 3. 신뢰도 — 평판 점수는 만들지 않는다

유저 100명 규모에서 평판 알고리즘은 동작하지 않는다. 표본이 없다.
대신 **싸고 효과가 확실한 장치**만 쓴다.

### 장치 목록 (효과 순)

| # | 장치 | 막는 문제 | 비용 |
|---|---|---|---|
| 1 | **사진 1장 필수** | 허위 장소, 장난 등록 | 거의 0. 등록률은 약간 하락 |
| 2 | **로그인 필수 (등록·제보)** | 익명 대량 오염 | 0 |
| 3 | **계정당 rate limit** (등록 5/일, 제보 10/일) | 악의적 대량 등록 | 0 |
| 4 | **동일 유저 중복 제보 무시** (월 단위 unique index) | 1인 다중 제보로 상태 조작 | 0 |
| 5 | **신규 계정(24h 미만) 등록 → 우선 검토 큐** | 일회용 계정 스팸 | 운영자 확인 시간 |
| 6 | **제보 가중치 0 처리** — 운영자 반려 3회 누적 시 | 허위 신고 상습범 | 0 |
| 7 | **운영자 수동 검토** | 나머지 전부 | 물량에 비례. 초기엔 하루 10분 |

6번은 **사용자에게 알리지 않는다.** 알리면 새 계정을 만든다. 조용히 무력화한다
(`profiles.report_weight = 0`. 제보는 정상 접수된 것처럼 보이지만 카운트에서 빠진다).

### 문제별 대응 정리

| 문제 | 대응 |
|---|---|
| **허위 장소** | 사진 필수 + 운영자 로드뷰 확인. 신고 1건이면 확인, 명백하면 `hidden` |
| **오래된 정보** | `last_verified_at` 배지 + `still_there` 제보 유도. 시간이 해결한다 |
| **잘못된 위치** | `wrong_location` 제보 2건 → 운영 큐. 운영자가 좌표 보정 |
| **악의적 등록** | rate limit + 신규 계정 우선 검토 + 반복 시 계정 정지 |
| **허위 신고** | 제보 dedup + 가중치 0 처리. `gone`을 자동 전환 안 하는 것 자체가 방어책 |
| **동일 스팟 중복** | 위 2절 |
| **장소 폐쇄** | `temporarily_closed` → 자연 복구 또는 운영자가 `removed` |
| **사진 저작권** | 본인 촬영만 허용 (약관 명시) + 신고 시 즉시 `is_hidden` → [결정 필요](OPEN_DECISIONS.md) 7 |

### 만들지 않는 것

- 사용자 신뢰 점수 / 레벨 / 기여도 랭킹 — 표본 부족 + 게임화가 오히려 품질을 떨어뜨린다
- 자동 이미지 검열 (AI 모더레이션) — 초기 물량에 비용이 안 맞는다. 신고 기반으로 충분
- 커뮤니티 투표형 모더레이션 — 유저 수가 임계치를 넘은 뒤 검토

## 4. 스케이트 금지 구역 · 사유지 정책

**등록은 허용하고, 경고를 표시한다.** (사용자 결정 사항)

이 정보는 스케이터에게 가장 실용적인 정보 중 하나다.
"여기는 가면 쫓겨난다"를 미리 아는 것이 이 앱의 가치다. 숨기면 앱이 무용해진다.

### 처리 방식

| 항목 | 처리 |
|---|---|
| `kickout_risk = 'banned'` / `status = 'no_skating'` | 빨간 배지 + **"이용을 권장하지 않습니다"** 명시 |
| `is_private_property = true` | "사유지 · 관리자 허가 필요" 배지 |
| 상세 화면 | 금지 스팟은 길찾기 버튼 옆에 경고 문구 동반 |
| 약관 | 앱은 장소 정보를 제공할 뿐 무단 출입·이용을 권장하지 않음을 명시 |
| 토지 소유자·관리자 요청 | **삭제 요청 창구 제공.** 요청 시 `hidden` 처리 후 검토 |

마지막 항목이 중요하다. 소유자 요청 경로가 없으면 분쟁이 법적 문제로 간다.
운영자 연락처를 앱과 스토어 페이지에 명시한다.

### 절대 하지 않는 것

- 무단 출입·침입을 안내하는 문구 ("담 넘어서 들어가면 됨" 등) → 신고 사유
- 금지 스팟을 추천·랭킹에 노출 (랭킹 자체를 안 만드는 이유 중 하나)

## 5. 운영 프로세스 — 어드민 앱을 만들지 않는다

초기 물량은 하루 10~30건이다. 여기에 어드민 UI를 만드는 건 순수 낭비다.

**Supabase 대시보드 + 미리 만든 SQL 뷰**로 운영한다.

### 필요한 뷰 3개

| 뷰 | 내용 |
|---|---|
| `admin_review_queue` | `moderation_flag` 있음 + 열린 제보 임계 도달 + 신규 계정 등록. 오래된 순 |
| `admin_gone_reports` | `gone` 제보 3건 이상 누적 스팟 + 증빙 사진 경로 |
| `admin_abuse_watch` | 반려 제보 2건 이상 누적 계정, 24시간 내 등록 3건 이상 계정 |

처리는 SQL 한 줄로 한다 (`update spots set status = 'removed' where id = ...`).

### 운영 루틴

| 주기 | 작업 | 예상 시간 |
|---|---|---|
| 매일 | `admin_review_queue` 확인 · 처리 | 10분 |
| 주 1회 | `admin_abuse_watch` 확인 | 5분 |
| 월 1회 | 180일 미확인 스팟 상위 목록 → 직접 확인하거나 커뮤니티에 확인 요청 | 30분 |

### 어드민 화면을 만들어야 할 시점

- 일일 검토 큐가 30건을 넘을 때
- 운영자가 2명 이상이 될 때
- SQL을 모르는 사람이 운영에 참여할 때

그전까지는 만들지 않는다.
